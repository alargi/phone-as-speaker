  1. 核心机制是"注册显示器"，不是"抓屏幕"。驱动向 Windows 上报一块虚拟显示适配器，DWM 把桌面（含这块虚拟屏）正常合成后，帧经交换链直接交付给 spacedesk，不经过任何截屏 API。这是它与 VNC / RDP / 截屏类方案的本质区别。
  2. 全链路五段：虚拟显示器枚举 → 帧交付与处理 → 帧内压缩 → TCP/UDP 传输 → 客户端解码渲染；再加一条反向输入回路（触摸/笔/键鼠 → 虚拟 HID 注入）。
  3. 压缩是件内（intra-frame）有损压缩，不是 H.264。官方参数为 YUV 4:4:4 / 4:2:2 / 4:2:0 色度子采样 + 0~100 质量滑块，且允许关闭压缩走 RGBA 32 位。网上"H.264 硬件编码"的说法在官方资料中找不到依据，且与带宽口径矛盾（详见第 4 节）。
  4. 传输明文无加密。官方明确说明客户端与服务端之间不加密，同网段内他人可抓取画面内容。
  5. 最大工程约束来自显示栈独占性。同类 hook 式显示驱动（DisplayLink、Duet Display、Splashtop XDisplay 等）与 spacedesk 不能共存。

2. 第一段：虚拟显示器枚举（全链的"地基"）

Windows 认为"有几块屏"，取决于显示适配器驱动的上报。spacedesk 的做法是加载一个符合 WDDM 规范的虚拟显示适配器，让图形子系统把它当作真实显卡。

为什么这一步是整个方案的支点

一旦系统承认了这块屏幕，后续所有事都变成"Windows 的正常多屏行为"：你可以在显示设置里拖动它的相对位置、设分辨率与缩放、按 Win+P 切扩展/复制、把窗口拖进去运行。spacedesk 不需要模拟窗口系统，也不需要猜"哪块区域变了"。

两条驱动技术路线

工程含义：因为驱动主体在用户态，spacedesk 不需要签内核驱动级别的兼容性妥协，出问题时服务可以被终止而不会拖垮系统；代价是帧数据要跨一次用户态/内核态边界，且必须依赖 IddCx 框架提供的表面（surface）交付机制。

3. 第二段：帧交付——为什么不需要截屏 API

这是整个方案最容易被误解的一环。三种"把画面拿到手"的思路对比：

机制代表方案传什么代价
传绘制指令RDP、X11、部分 VNC 模式 窗口/字体/坐标等语义指令，客户端重建界面 带宽省，但画面与本地不完全一致；高动态场景失真明显，不适合"当第二块屏"
传像素（抓屏）VNC、多数截屏式投屏、DXGI Desktop Duplication 已合成的桌面位图 需额外一次显存→内存拷贝；CPU/带宽压力大，帧率与延迟受抓屏节拍制约
进合成路径spacedesk（IddCx） 虚拟屏自身输出的合成结果 无需截屏 API，也无需猜测变化区域；代价是必须占用一个"显示器名额"并独占显示栈钩子
关键推论

spacedesk 之所以能在 60fps 下保持较低 CPU 占用，并不是因为编码有多强，而是因为它在数据产生的地方直接取数，省掉了整条"显示输出 → 显存 → 系统内存 → 编码器"的中间搬运链。反过来，这也解释了为什么它无法用于"远程访问一台没有安装驱动的机器"——没有虚拟显示器，就没有数据源。

帧进入服务后的处理

  1. DWM 按节拍合成桌面，虚拟显示器对应的表面被填充；
  2. IddCx 框架把该表面交付给 spacedesk 的用户态驱动；
  3. 色彩空间转换（RGB → YUV）与色度子采样（按设置的 4:4:4 / 4:2:2 / 4:2:0）；
  4. 按质量参数做帧内压缩，产出待发送的图像数据；
  5. 交给 spacedeskService.exe 打包发送。

4. 第三段：压缩编码——需要纠正的一个流行误解

纠偏：spacedesk 用的是 H.264 吗？

大量中文技术博客（其中相当一部分是 AI 生成内容）声称 spacedesk 使用 H.264、调用 NVENC / Quick Sync 硬件编码，甚至给出 x264 参数表。这些内容在官方文档、官方 SDK 说明与官方论坛答复中都找不到任何依据，且与官方给出的可调参数互相矛盾。

官方文档实际披露的可调参数

参数官方取值说明
压缩性质有损图像压缩（lossy）官方明示会降低画质与色深
色度子采样YUV 4:4:4 / 4:2:2 / 4:2:04:4:4 不丢色彩信息（24bit）；4:2:2 减 1/3（16bit）；4:2:0 为默认（12bit，性能最佳）
压缩质量滑块0 ~ 100，默认 70100 = 不压缩，0 = 最大压缩
关闭压缩可用Windows Viewer 可设 OFF，直接走 RGBA 32 位
帧率Viewer 端可设Windows / Android / iOS 均提供设置
分辨率上限Windows/HTML5 ≤ 4096×2160iOS / Android 自定义分辨率不得超过设备原生分辨率

为什么这组参数只能是帧内压缩

  • "能关掉压缩走 RGBA32"是决定性证据。H.264 的码流结构与 RGBA 位图不是同一回事，不存在"关闭压缩后输出 RGBA"的选项；而帧内编码（JPEG / DCT 类）天然支持"质量=100 即近似无损"或"整体旁路"。
  • 色度子采样是画面级参数，不是帧间参数。4:2:0 / 4:2:2 / 4:4:4 是每帧独立采样的选择，H.264 虽也使用 4:2:0，但它不会以"用户可在客户端切换采样格式"的形式暴露。
  • 带宽口径对不上。官方给出的最低带宽要求约 50 Mbit/s（BETA 期口径）。而 1080p60 场景下 H.264 的典型码率是 5–15 Mbps 量级——若真用 H.264，官方不可能把门槛定在 50 Mbps。

带宽账：一帧到底有多大

以 1920×1080 @60fps 计算各格式的未压缩裸码率（可精确计算）：

安全性：明文传输

官方明确声明：客户端与服务端之间不加密

官方文档原文即"network protocol ... No encryption transmitting data between client and server. Therefore all information transmitted is potentially available to everybody in the network."这意味着同一局域网内的任何人都可能获取你副屏上的画面内容与回传的输入事件。在公共 Wi-Fi、办公网、酒店网络等不可信环境中使用时，应视为屏幕内容公开。如需加密，只能依赖网络层手段（VPN / WPA3 / 独立隔离链路）。

7. 反向链路：输入回传与虚拟 HID

副屏上的一次点击要变成主机的鼠标事件，走的是与视频流完全相反的方向：

客户端捕获输入触摸 / 手写笔 / 虚拟键鼠
→
经 28252 回传坐标与事件编码
→
spacedeskService坐标映射与坐标变换
→
虚拟 HID 注入当作真实硬件设备

关键点：注入不是"模拟鼠标 API 调用"，而是通过虚拟 HID 设备把事件喂给 Windows 输入栈（spacedeskDriverHid.dll + spacedeskKtmInputMouse.sys / spacedeskKtmInputKeybd.sys）。系统把它当作一块真实的键鼠硬件，因此所有应用（含受保护的游戏、需要原始输入的绘图软件）都能正常识别——这也是 spacedesk 能自称"软件 KVM"的技术基础。

坐标映射的两种模式

  • 绝对模式（absolute）：触摸点直接映射为屏幕绝对坐标，等同于数位板/触摸屏行为。
  • 相对模式（relative）：触摸滑动手势映射为指针位移，等同触控板行为。适合小屏手机操控大屏桌面。

8. 端到端时延预算

估算官方未公布时延分解数据，下表为按各环节机理给出的量级估算，用于定位瓶颈，不作为官方指标。

环节典型量级决定因素优化方向
桌面合成与帧交付≥1 个显示节拍（60Hz ≈ 16.7ms）DWM 合成节拍、虚拟屏刷新率降低副屏分辨率/刷新率
色彩转换与抓帧1 ~ 5 ms用户态数据搬运、子采样格式选 4:2:0
帧内压缩5 ~ 15 ms分辨率 × 帧率 × 质量滑块；CPU 单核性能下调质量滑块（70 → 40~50）
网络传输1 ~ 3 ms（千兆有线）
5 ~ 20 ms（Wi-Fi 5/6）		链路介质、拥塞、丢包与重传有线 > Wi-Fi Direct > USB 共享 > 普通 Wi-Fi
客户端解码3 ~ 10 ms是否硬件解码；设备 SoC 能力换用支持硬解的较新设备
渲染与显示≥1 个显示节拍客户端屏幕刷新率与 VSync关闭客户端省电模式
合计（理想）约 40 ~ 80 ms有线直连 + 高画质—
合计（普通 Wi-Fi）约 80 ~ 200 ms无线链路为主要瓶颈改有线或 Wi-Fi Direct

两点结构性结论：其一，即使其它环节全部归零，两端各一个合成节拍就锁死了约 33ms 的下限，所以它不可能达到本地显示器的响应水平；其二，无线场景下链路质量而非编码能力才是主导变量——这解释了为什么"换更好的路由器"往往比"调编码参数"有效得多。

10. 工程边界与已知限制

显示栈独占性（最容易踩的坑）

官方明确列出与 spacedesk 不能共存的同类 hook 式显示驱动产品：

DisplayLink · Duet Display · Fresco Logic · MCT · Microchip/SMSC · OSBase（被 Duet、Fresco Logic 等使用）· Splashtop XDisplay / Extended Display HD

注意卸载残留

部分使用 OSBase 驱动的产品（如 Duet Display、Fresco Logic）卸载时不会清理干净，残留驱动仍会导致 spacedesk 报"Incompatible Display Hook Driver Detected"。需手工检查并清除 ddkmd / ddkmdldr / ddmgr 等残留项。

其它已知冲突与限制

项目现象
NVIDIA ShadowPlay（屏幕录制）开启时 Viewer 报错 1-2-0
多 GPU（SLI / CrossFire）官方明确不支持，启用后无法正常工作

AP 隔离 / 客户端隔离无线场景下阻断设备互访，只能改路由器配置

安全与隐私

  • 明文传输：画面与输入事件在局域网内可被嗅探（官方明示）。
  • 输入注入权限：虚拟 HID 能产生系统级键鼠事件，相当于把主机的完整控制权交给了接入的客户端——在不可信网络下不要保持服务长期开启。
  • 驱动签名：安装需加载显示驱动，企业环境中 Secure Boot / 驱动强制签名 / 组策略可能拦截。

客户端搜不到主机发现机制关闭 VPN；放行 spacedeskService.exe；改手动输 IP；确认未开 AP 隔离
连上但副屏黑屏显示模式主机按 Win+P 切到"扩展"
驱动报错、黄叹号驱动层检查 System32\drivers\UMDF\spacedeskDisplayUmode1_x.dll 是否存在；设备管理器禁用再启用 spacedesk Graphics Adapter
